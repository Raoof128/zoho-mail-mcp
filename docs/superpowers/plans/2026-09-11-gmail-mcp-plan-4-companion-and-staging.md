# Plan 4: local companion and upload staging

Status: design revision 3, approved for inline implementation on 2026-09-12. This revision resolves the pasted review's B1–B6 and M1–M12 with concrete design decisions. These are requirements for future implementation, not shipped guarantees. [Review dispositions and verification](../reviews/2026-09-11-plan-4-review-resolution.md) distinguish adopted recommendations from refinements.

## 1. Baseline, scope and authority

Plan 3 merged at `11b1fd9`. The earlier gauntlet ran `npm run verify` with exit 0: 7 shared tests and 243 Workers tests passed. Existing code provides Google OAuth, 38 Worker tools, approval and policy enforcement, staging download/ACK routes and bounded R2 ingest. Upload tickets and the local companion do not exist yet. Historical test counts establish the baseline only.

Use Approach 1: a thin macOS stdio companion, with the Worker retaining Gmail credentials, account ownership, upload policy and browser approvals. The companion controls local paths and transfers attachment bytes outside model context. Keep three tools: `save_attachment`, `stage_file`, `list_roots`; provide login, logout, setup, status and repair through an owner-facing CLI.

V1 uses a dedicated attachment write folder, optional owner-configured read roots, and **overwrite = deny only**. An existing file is never replaced, even with a client confirmation. Reject configuration containing `overwrite: ask`; do not downgrade it silently. Approved replacement is deferred as the named item `P4-OVERWRITE`, requiring a separate design and review. This retires the current unresolved overwrite mechanism rather than presenting it as implemented protection.

Plan 5 retains protected Gmail round trips, send reconciliation and its wider fault-injection programme. Plan 4 owns the fault tests needed for local transfers, upload tickets and cleanup. Do not defer those to Plan 5.

This revision changes spec 2.4/3.6/4.5: logical root IDs, no overwrite, ticket generations, native Keychain access and transfer continuation. Before implementing, reconcile those sections and the end-to-end client instructions with this design. The old spec remains a historical design input, not permission to implement conflicting behaviours.

## 2. Tools, roots and canonical metadata

The tool inputs are:

| Tool              | Input                                                                                     | Result                                                                                    |
| ----------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `list_roots`      | none                                                                                      | Root ID, owner-selected label, read/write flags and available bytes; no absolute paths.   |
| `stage_file`      | `account`, `root_id`, `relative_path`; optional `transfer_id`, optional `idempotency_key` | Pending approval with transfer ID and URL, upload status, or the original staging handle. |
| `save_attachment` | `handle`; optional `root_id` defaulting to `attachments`, `subdir`, `filename`            | Logical destination, size, digest, local publication status and separate ACK status.      |

Root IDs are stable owner-controlled identifiers. Labels are bounded display text. CLI/configuration alone shows absolute paths. No tool, MCP roots notification or helper command may expand configured grants. Additional write roots require a separate owner configuration action; adding a read root does not grant writes.

Private state is `~/.config/gmail-mcp/` for configuration and `~/Library/Application Support/gmail-mcp/` for journal, locks and spool. Permissions are 0700 for private directories and 0600 for files. Refuse any root that is an ancestor or descendant of either private tree, or an alias of one. Resolve existing directory identities through filesystem descriptors and compare ancestry in both directions, including case/Unicode equivalents. Do not use string-prefix comparison. Reject nested/duplicate root aliases in V1. If private directories cannot be established and verified, refuse startup. Validate grants again after owner configuration changes; running transfers retain their original root ID and identity.

Protocol strings use NFC. Canonicalize filename and metadata before the approval hash; persist and return that exact representation. Reject caller filenames containing separators, NUL, `.` or `..`; sanitize untrusted remote suggested basenames by NFC normalization and replacement of control/bidi characters. Enforce the existing 255 UTF-8 byte bound without splitting scalars. Limit subdirectories to 16 nonempty components and relative paths to 1024 UTF-8 bytes; reject absolute paths and dot components. The filesystem's exclusive operation decides name collisions, including case and Unicode equivalence. Never infer uniqueness from unequal JavaScript strings.

Accept empty regular files through 25 MiB inclusive. Metadata is strict `{filename, size, mime, sha256}` with the existing media-type grammar and lowercase 64-digit SHA-256. Resolve the account alias to immutable account ID before remote intent hashing. Canonical intent is versioned and includes account ID and metadata; transfer IDs and pending IDs are not part of the content hash. No filename, type or byte change is permitted after approval without a new intent.

## 3. Native macOS helper

Use one Swift executable, built with Swift Package Manager, with a small C target exposing Darwin filesystem calls where needed. TypeScript owns MCP and HTTP orchestration. The helper owns Security.framework calls, descriptor-relative file operations, SQLite receipts, snapshots and process locks. Use OS frameworks and SQLite; do not add a shell-based Keychain adapter or generic command runner.

Support macOS 26.6 or newer initially, subject to runtime capability checks. The probe on macOS 26.6.2 confirmed `renameatx_np` with `RENAME_EXCL | RENAME_NOFOLLOW_ANY | RENAME_RESOLVE_BENEATH`: a new name succeeded; existing destination, symlinked parent and parent traversal failed. This is primitive evidence on one machine, not proof of the finished helper. Require local volumes supporting the flags, exclusive rename and required synchronization. Fail closed on unsupported filesystems, flags or durability operations; do not fall back to ordinary rename. Network filesystems are outside V1 support.

Launch the helper by a fixed absolute installed path, without a shell. The helper reads owner configuration itself. Its narrow protocol uses versioned, typed messages on inherited private pipes: root inspection, snapshot creation/streaming, save preparation/publication, receipt recovery, and Keychain/auth transaction operations. Control frames are capped at 64 KiB. Transfer bytes travel in bounded binary frames or dedicated inherited pipes, never JSON/base64 in MCP results. Reject unknown operations, extra fields, invalid handles and excess bytes. Close descriptors and cancel unfinished operations on pipe EOF or parent exit. The helper has no network listener and no elevated privileges.

Package the helper with source, build instructions, version/capability handshake and an integrity manifest. A developer build may use a local signature; packaged distribution needs a stable signing identity and a tested Keychain access policy. Do not claim that an unsigned development build has passed distribution signing or live Keychain access checks.

### Filesystem algorithm and boundary

1. Open configured roots and private directories as directories, verify owner/permissions and record device/inode identity. Resolve macOS system path aliases during owner setup; thereafter reject symlink traversal within configured roots. Roots are anchored directory identities for the helper session, not a promise about an absolute pathname after someone renames it.
2. Open relative paths beneath the root descriptor with `O_NOFOLLOW_ANY | O_RESOLVE_BENEATH`; verify the resulting descriptor with `fstat`. Reject non-regular source files, multiply linked source files and unexpected volume crossings. Use nonblocking open where needed so a FIFO cannot stall validation. Recheck root identity against configuration when starting a new operation; require owner reconfiguration if it changed.
3. For saves, create an unpredictable temporary file with exclusive creation and mode 0600 in the destination filesystem. Reserve the temporary-name namespace from tool requests. Create any missing subdirectory components through directory descriptors, rejecting symlinks and existing non-directories. Record the root-relative temporary path and descriptor identity in the private journal.
4. Stream into that descriptor, enforce length, compute SHA-256 and compare against the authenticated response metadata. Sync the file before marking the receipt `verified`. Never copy executable permissions or remote extended attributes.
5. Publish using the root descriptor and full validated root-relative paths for both names in `renameatx_np`, with all three flags. Using only a previously opened parent FD would not by itself prove that the parent remained beneath the root. Before the call, require the temporary descriptor/path identity to agree. Missing/replaced paths fail; `EEXIST` is a no-clobber refusal. Sync the destination directory and record publication before sending ACK.
6. On restart, recover using recorded identity, size and digest. A file merely existing at the destination is insufficient. If identity or content is ambiguous, return `publication_unknown`; do not overwrite, repeat publication or ACK based on a guess.

The supported threat boundary is model-directed traversal, symlink following and destination clobbering. Tests cover root/parent substitution and verify no write through a substituted symlink. This is not a sandbox against an arbitrary malicious process running as the same macOS user, which could alter configuration, receipts or the process itself. Pinned root identity also does not promise continued membership under an old absolute pathname after external renaming. State these limits in SECURITY.md instead of claiming protection from every concurrent filesystem mutation.

### Keychain and authentication locks

Use Security.framework generic-password APIs (`SecItemCopyMatching`, `SecItemAdd`/`SecItemUpdate`, `SecItemDelete`) directly. Store the access/refresh pair and expiry as one versioned credential item, keyed by Worker origin and generated client ID. No credentials in argv, environment, SQLite, ordinary logs or tool results. The helper returns credentials only over its inherited private control pipe to the companion. Do not invoke `security -w` or `security -p`.

Use `flock` on a stable private per-authority lock file shared by helper instances. Never unlink/recreate a held lock file. Acquire within 30 seconds; read Keychain after acquisition. The helper holds the descriptor while the companion performs a bounded token exchange and accepts a commit only on that same live auth transaction. A crashed helper releases the kernel lock; its old transaction cannot later commit through another instance. Persist rotated credentials before unlocking. Lock acquisition failure returns `auth_busy` rather than refreshing concurrently.

Logout takes the same lock, commits a durable logged-out auth epoch, attempts revocation with a 30-second timeout, deletes the Keychain item, then unlocks. If the helper crashes after recording logout, startup finishes deletion before permitting authenticated work. A refresh that predates the epoch cannot restore credentials. Distinguish local logout from unconfirmed remote revocation.

## 4. OAuth contract

Use the generated companion client ID shown on Accounts, not the literal string `companion`. Installed `@cloudflare/workers-oauth-provider` 0.10.3 already supports ephemeral loopback ports; `worker/test/oauth.test.ts` exercises port 61234 against no-port registration. Keep this test as a pinned-version regression and add callback rejection tests.

Bind `127.0.0.1` on an OS-selected port before opening the browser. Use `/callback`, PKCE S256, a random one-use state and a 10-minute login deadline. On bind failure do not launch the browser. Accept only the expected callback method/path/Host and exactly one state, issuer and code on success. Reject missing, duplicate or mismatched parameters, callback replay and provider errors without token exchange. Close the listener on completion, cancellation or deadline; an invalid unrelated request must not consume a valid login state.

The expected issuer is the configured HTTPS Worker origin without a trailing slash. Require discovery `issuer` and callback `iss` to match it exactly. This provider advertises and emits `iss`, so a missing issuer is a failure. The resource audience is separately `<origin>/staging`, and the requested scope is only `staging`.

Pin discovered authorization, token and revocation endpoints to the configured origin and expected routes. Use `redirect: error` for discovery, token exchange, refresh, revocation and authenticated staging requests. Do not follow redirects manually. Bound discovery/control responses to 64 KiB and network control requests to 30 seconds. Browser navigation through the expected authorization flow is separate from token-bearing HTTP calls.

Registration recovery must handle the existing persistent `pending` sentinel. Replace it with an attempt record, fencing token and a 2-minute lease. Restrict repair to the owner with recent authentication. A timed-out creator cannot finalize without its fencing token. Before retrying creation, reconcile provider client records against the attempt marker; remove or recover orphan candidates and any associated grants. An unknown client from an interrupted attempt must not receive a scope merely because it is absent from the completed companion setting. The installed provider supports paginated `listClients` and `deleteClient` including grant revocation. It stores explicit client fields rather than arbitrary metadata: put the persisted random attempt marker in a reserved `clientName` namespace, reject that namespace in public registration, and reject marked-but-unfinalized clients at authorization instead of falling through to MCP scope. Match the marker and expected registration metadata before repairing; ambiguous matches require owner intervention. KV listing/lookup absence is eventually consistent and cannot prove no orphan exists. Keep the attempt quarantined and reconcile again; never automatically recreate a client merely because a lookup returned empty.

## 5. Local journal and first-response recovery

Use SQLite through the helper with `journal_mode=WAL`, `synchronous=FULL`, `fullfsync=ON`, `checkpoint_fullfsync=ON`, foreign keys and prepared statements. Verify effective pragma values at startup. Sync newly created private-directory entries. Durable means acknowledged journal transactions plus synchronized file data/directory entries on a supported local filesystem; power-loss claims still require hardware/volume validation. A corrupt journal fails closed and preserves files for owner repair.

Before snapshot creation, reserve a local transfer row and its byte/count budget in one transaction. Authenticate first and obtain the owner ID from a staging-scoped `GET /staging/identity` response, never from unverified token text. Scope all local requests, receipts and results to that owner, Worker origin and client ID. The automatic request key includes that identity plus account alias, root ID and normalized relative path. A supplied idempotency key has a separate unique constraint on owner/origin/client/key and binds the full source request hash; changing the source cannot create a second row under that key. Switching owners makes earlier records inaccessible, while retaining them for their original owner. Under a cross-process request lock, create and verify the private snapshot, record its descriptor identity, size, SHA-256, canonical metadata and local request hash, then mark the row ready. The Worker resolves the immutable account ID and computes its server intent hash; record those returned facts when the first response or status recovery arrives. Recover existing transfers by owner/transfer ID before resolving an alias again, so alias changes cannot redirect a retry to a different account. Only after this durable record exists may the companion create a remote intent.

A retry without `transfer_id` selects the same request key before opening the live source again. Exactly one retained row resumes or returns its recorded result, including completion; multiple candidates return `ambiguous_transfer` with logical IDs and perform no remote side effect. Never infer a fresh transfer because the first tool response was lost. Keep automatic request-key recovery for seven days. To intentionally stage a new snapshot of the same path during that window, supply a new explicit idempotency key. Reusing a supplied key with a different source request fails. Resumption always uses the original snapshot even if the source path changed; report that fact with the snapshot digest. A missing snapshot requires a new intent and cannot reuse approval.

Persist `transfer_id` before the first remote call. IDs use 32 random bytes encoded base64url and are scoped to the configured authority/owner. The Worker binds `(user_id, transfer_id)` to immutable account ID and intent hash. A repeated intent recovers the same pending row/status. Snapshot preparation failures remain recorded; startup resolves incomplete snapshots before any remote call.

Save receipts record handle, root ID, relative destination, size, digest, temporary device/inode, published device/inode when known, publication state, ACK state and timestamps. States are `prepared → verified → published → acknowledged`, with explicit `failed` and `publication_unknown`. Reserve the destination and receipt under a cross-process lock, commit before publication, and recover a crash between rename and journal completion by checking the recorded temporary file identity at the destination plus size/digest. If the destination changed, preserve uncertainty and do not ACK. Repeated saves for the same handle/destination return the same receipt; a conflicting destination request fails until the owner makes an explicit new save choice.

## 6. Worker transfer and ticket model

Ticket IDs are opaque **identifiers, not credentials**. Choose the review's simpler model: `PUT /staging/<ticket_id>` requires the OAuth staging bearer, owner/account binding and the current generation. There is no separate upload-proof secret. Knowing a ticket ID alone grants no access. Application audit logs should still minimize identifiers; OAuth credentials remain secret. Ticket IDs stay in companion-to-Worker traffic and need not appear in ordinary MCP results.

`POST /staging/intent` carries `transfer_id`, account alias, canonical metadata and an optional explicit retry request. Use explicit modes: `ensure` creates or recovers the intent and generation 1; `status` only reads existing state; `retry` requests one replacement for an expired or abandoned generation. It requires `expected_generation` and a stable `retry_request_id`, both persisted by the companion before the call. Bind that retry ID to the old generation and its resulting generation in D1. A repeated retry returns the recorded resulting generation/status even if it has since expired; advancing again requires a new explicit retry ID. Integrity-failed transfers cannot retry. All modes require matching owner/account/intent. Status retries never issue another ticket. A response includes transfer state, pending approval when applicable, and the current ticket ID/generation only when issued. A completed transfer returns its original handle or `completed_handle_expired`; it never restages bytes silently.

Persist these records in append-only migration 0004:

| Record               | Required fields and constraints                                                                                                                                                                                                                                           |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `upload_transfers`   | Owner, transfer ID, immutable account ID, canonical metadata/hash, payload version, pending/operation IDs, authority deadline, active generation, terminal state, original handle and retention deadline. Unique owner/transfer; composite ownership foreign keys.        |
| `upload_generations` | Transfer, generation number, unique ticket ID, state, issuance expiry, admission/lease deadlines, captured account credential version, deterministic R2 key, byte reservation and cleanup state. Unique transfer/generation; partial uniqueness for an active generation. |
| Admission/accounting | Transactional owner/global counters or unique slots for all limits in section 8, plus per-generation reservations and retention metadata. Counts derive from persisted state, never process-local semaphores.                                                             |
| Download/ACK state   | Download lease deadline, cleanup state and owner/account-bound ACK tombstones keyed by handle; preserved independently of the staging object row.                                                                                                                         |

Transfer states are `awaiting_approval`, `authorized`, `in_progress`, `completed`, `failed`, `expired`, `denied`. An `allow` intent gets an authority deadline 15 minutes after creation. An `ask` intent uses the existing pending action's expiry; approval does not extend it. Retries may reuse approval only before that deadline, for the unchanged snapshot/hash and still-permitted account/policy. A completed transfer is terminal for all ticket issuance.

| Current generation state        | Event and guard                                                                                                        | Next state and effect                                                                                              |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| none                            | Authorized transfer, capacity available, current policy permits                                                        | `issued`, generation 1, expires at min(now + 60 seconds, authority deadline).                                      |
| `issued`                        | Expiry reached before admission                                                                                        | `expired`; no PUT allowed.                                                                                         |
| `issued`                        | Matching bearer/intent, active account, current policy permits, capacity reserved, before expiry                       | `uploading`; one atomic claim, capture account credential version and five-minute lease.                           |
| `uploading`                     | Complete byte count/hash, R2 write succeeds, current generation and live lease                                         | `stored`; persist verified object facts under the same fence.                                                      |
| `stored`                        | Completion batch wins with current active generation, live lease, and account active with unchanged credential version | `completed`; publish one staging row/handle, settle pending/operation/audit together.                              |
| `uploading` or `stored`         | Lease expires, stream fails, or recovery fences the writer                                                             | `abandoned`; no late publication. Persist cleanup debt.                                                            |
| `issued`, `uploading`, `stored` | Policy refuses at admission, invalid bytes, revoked account or changed credential version                              | `failed`; no handle, terminalize the transfer for integrity/revocation errors.                                     |
| `expired` or `abandoned`        | Explicit retry, previous generation fenced, authority deadline valid, unchanged intent, limits permit, generation < 3  | Create next `issued` generation in the same transaction that advances active generation. Old ticket stays invalid. |
| Any terminal generation         | Repeated PUT or stale generation                                                                                       | Refuse without accepting the body; status may return recorded outcome.                                             |
| Transfer `completed`            | Any ensure/status/retry call                                                                                           | Return original result; no new ticket, pending action or handle.                                                   |

Network interruption/timeout can leave a retryable `abandoned` generation. Hash mismatch, wrong length or revoked/reconnected account cannot reuse that transfer's approval. Cap generation count at three. After authority expiry or exhausted generations, require a new explicit local idempotency key and fresh intent/approval. No automatic byte retransmission: the companion may recover status automatically, but requests a replacement only on a subsequent user/tool retry. At most one generation can admit or publish; older network requests can still exist, which is why fencing and cleanup debt are separate.

### Admission, completion and recovery

Before claiming any pending row, require `attachment.stage_upload`, `tool=stage_file`, payload version 1 and matching metadata/account. Generic MCP `execute_pending` rejects staging actions before claim; staging routes reject Gmail actions before claim. Create the first operation, claim the pending action and issue generation 1 in one D1 batch. Later generations remain attached to that operation; never claim the same pending action twice.

D1 zero-row updates do not fail a transaction. Use the existing `_assert` pattern to ensure that a failed CAS rolls back generation creation, accounting and publication. Evaluate account and policy inside the admission transaction or assert a captured policy revision against a revision incremented by policy edits. Include blocked-extension configuration in the checked revision. At issuance/admission, `deny` refuses and terminalizes the transfer. If current policy is `ask`, require a recorded browser approval for this same immutable intent; an earlier `allow` decision is not approval. An allow-to-ask change creates or recovers the one pending action for this transfer and returns `awaiting_approval` without accepting bytes or extending its original authority deadline. An already-issued ticket is fenced before that transition. Ordinary policy changes committed after admission need not cancel admitted bytes. Account revocation is stricter: the completion batch requires active status and exactly the credential version captured at admission. Revocation followed by reconnect still invalidates the transfer; active status alone is insufficient.

Choose a fixed five-minute upload lease, without heartbeat. Authority expiry prevents new admission or retry; an already-admitted generation may settle until its own lease expires. Neither ensure nor cron expires that live generation solely because the admission authority ended. The companion aborts the PUT after four minutes; the Worker bounds body receipt to four minutes and attempts R2/settlement only while the five-minute lease is valid. A slow upload that misses the boundary fails with explicit retry status. Timers express application deadlines, not proof that an underlying storage write has ceased. A late writer must lose its completion CAS.

Require `Content-Length` exactly equal to approved size, identity content encoding and matching media type. Count and hash actual bytes; reject short/long bodies and unsupported headers before storage/publication. Split current `ingest` into byte verification, object storage and transactional publication. Do not call unchanged `ingest` and then create the transfer record afterward.

Persist `stg/upload/<owner>/<transfer_id>/<generation>` as the R2 key before accepting bytes. Only that admitted generation may write it, once. Store verified actual size/digest, intent hash and generation as Worker-written metadata; caller-supplied expected digest is not independent integrity evidence. Recovery rehashes stored bytes or checks a verified storage checksum before publishing from `stored`. A crash after R2 success but before D1 `stored` may safely abandon and clean that object; V1 need not infer successful completion from its mere existence.

The completion batch publishes staging metadata, saves the original result, marks transfer/generation completed, settles operation/pending state, redacts terminal payload and appends outcome audit. R2 remains outside the transaction. A failed or expired generation keeps its deterministic key and charged bytes as cleanup debt. Recovery fences first, then deletes. A late R2 write can recreate an object after deletion, so a single successful delete is not proof that the debt can be released.

Release abandoned-generation storage charge only after the writer has acknowledged termination and cleanup confirms deletion. If the writer's status is unknown, retain the charge and generation record, retry cleanup, and report it through owner status. The one-day R2 lifecycle is a backstop, not proof of writer quiescence. Budget exhaustion from unresolved debt fails closed; owner repair must quiesce relevant writers and verify cleanup before releasing reservations. This sacrifices availability under ambiguous infrastructure failure to avoid pretending storage is bounded when late writes remain possible.

Scope the existing cron's claimed/executing send recovery away from `attachment.stage_upload`. Use upload-specific recovery for generations and a transaction assertion for each transition. Emit intent/outcome audit with IDs/counts, never local paths, file content, tokens or raw request headers. Purge pending payloads on terminal completion, failure, denial and expiry; retain hashes/status needed for the seven-day result window.

## 7. Download leases, publication and idempotent ACK

Authenticated `GET /staging/<handle>` must atomically admit a five-minute download lease before opening R2. Require owner match, download direction, an unconsumed row, no cleanup claim and an unexpired admission window. Extend protection to the admitted lease deadline, capped at one hour after original staging creation; repeated GET cannot retain bytes indefinitely. Limit simultaneous downloads as below. Client save deadline is four minutes. Lease expiry prevents another admission; a local file already verified/published remains a local success even if remote cleanup later becomes unconfirmed.

Change purge from select/delete into an atomic `available → deleting` claim that requires `(expired OR consumed) AND no live lease AND no reservation`. GET can lease only `available`; purge deletes only the generation/row it claimed. Recheck reservations and consumption under that claim. A row selected earlier for cleanup cannot be revived by GET and then deleted from underneath it. Read-lease expiry cannot by itself prove an in-flight transport stopped, so receipt recovery remains mandatory.

After durable local publication, `POST /staging/<handle>/ack` atomically records consumption and an owner/account-bound tombstone. First ACK returns `200 {acknowledged: true, replayed: false}`; repeats during seven-day tombstone retention return `200 {acknowledged: true, replayed: true}`. Match tombstone ownership before returning status. The tombstone survives R2 and staging-row deletion. It means the server recorded acknowledgement, not that R2 deletion already finished. After retention, 404 means unknown/unavailable, not successful consumption.

To ACK an admitted save after object TTL, consult the retained admission/handle record; accept only a valid owner-bound save admitted while the object was readable, within the seven-day recovery window. Account revocation prevents new GET admission; cleanup-only ACK of a prior save remains permitted. Store admission metadata long enough for this check. A first ACK without either a valid staging/admission record or tombstone returns 404.

## 8. Enforced V1 budgets and retention

These are conservative product limits, not measured capacity claims. Raising them requires concurrent-runtime measurements and an owner/deployment configuration change. Bytes mean binary bytes; MiB = 1,048,576 bytes.

| Domain                                               | Limit                                                      | Enforcement and release                                                                                                                                                                                                   |
| ---------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| File                                                 | 25 MiB, including empty files                              | Preflight plus byte counting on both ends.                                                                                                                                                                                |
| Worker pending upload intents                        | 16 per owner, 32 deployment-wide                           | D1 creation transaction; release on terminal state.                                                                                                                                                                       |
| Worker issued tickets                                | 4 per owner, 8 deployment-wide                             | D1 issuance/expiry transaction; one active generation per transfer.                                                                                                                                                       |
| Worker active upload leases                          | 1 per owner, 1 deployment-wide                             | D1 admission slot; release by fenced settlement/recovery.                                                                                                                                                                 |
| Worker staging materialization                       | 1 admitted large-buffer operation deployment-wide          | Cover upload ingest and existing Gmail attachment materialization; shared admission helper prevents nested double-acquisition. Admission count is not a strict isolate-memory proof when an expired worker remains alive. |
| Worker active staging downloads                      | 2 per owner, 4 deployment-wide                             | D1 five-minute leases, released on completion/expiry.                                                                                                                                                                     |
| Worker retained staging bytes                        | 250 MiB per owner, 500 MiB deployment-wide                 | Reserve before upload/attachment materialization. Count completed objects, active reservations and abandoned-generation cleanup debt. Release only through proven cleanup.                                                |
| Worker generations                                   | 3 per transfer                                             | D1 generation CAS. Each generation reserves its possible object bytes.                                                                                                                                                    |
| Worker retained transfer/admission/tombstone records | 1,000 per owner, 2,000 deployment-wide, seven days minimum | Reserve recovery-record capacity before admitting new work; reject new work rather than evict evidence early.                                                                                                             |
| Companion snapshots                                  | 4 files, 100 MiB across all instances                      | SQLite reservation before copy; release after unlink and journal update.                                                                                                                                                  |
| Companion simultaneous snapshot reads                | 1 across all instances                                     | Helper-managed SQLite lease and process ownership; prove termination before reuse after a crash.                                                                                                                          |
| Companion simultaneous saves                         | 1 across all instances; 25 MiB temporary-save bytes        | Reserve before GET; covers private temporary file until publish/removal.                                                                                                                                                  |
| Companion receipts                                   | 1,000 records, 16 MiB metadata budget, seven days          | SQLite admission; refuse new transfers at capacity. Cleanup-debt/unknown records are not evicted to make room.                                                                                                            |
| Local free-space floor                               | 100 MiB after reserving the maximum incoming file          | Check on the destination/spool volume; handle ENOSPC despite preflight.                                                                                                                                                   |

Snapshots expire 15 minutes after their creation, matching the maximum intent window conservatively. Keep them pinned during an already-admitted attempt, capped at its five-minute lease plus one minute for cleanup; never unlink a file while the helper is still using it. Completed upload snapshots can be deleted once the original remote result is durable. Retain their hashes and request keys for seven days. Failed or expired local request keys return their prior status; a new explicit idempotency key creates a fresh attempt.

Server status/result retention is seven days after terminal completion; unfinished transfers expire under their authority deadline and retain recovery evidence. Published staging handles still use the existing 30-minute TTL, plus existing holds for approved send operations. A seven-day transfer result does not promise the handle remains usable for seven days. ACK tombstones last seven days from acknowledgement. Cleanup debt retains its quota reservation until resolved even if its diagnostic record is older.

A local semaphore may reduce contention but cannot authorize work. Use D1 batches for cross-Worker accounting and SQLite transactions plus process locks for cross-companion accounting. Expired admission slots fence publication; they do not prove an old allocation was freed. Measure the worst concurrent mix, including existing download base64 materialization, and do not claim that this admission table alone proves the 128 MiB isolate ceiling.

## 9. Implementation sequence and acceptance

1. Reconcile design amendments, add shared contracts and migration 0004 with state constraints, accounting and recovery records. Write failing ownership, policy-revision, generation and result-replay tests before handlers.
2. Separate staging verification/storage/publication, implement intent/PUT and upload-specific recovery. Add cleanup fencing to downloads before adding GET leases and ACK tombstones. Exercise D1/R2 interruption points with deterministic barriers.
3. Build the native helper and its capability probe, Keychain adapter, private SQLite journal, roots, snapshots and exclusive publication. Test synthetic files and an isolated test Keychain; never use real account credentials in fixtures.
4. Add the companion workspace, owner CLI and OAuth flow, then stdio tools and both supported elicitation wire forms. Verify URL approval/text-link continuation using stored transfers. V1 has no overwrite form elicitation.
5. Run local companion-to-Worker round trips, verify setup/registration repair and cross-process recovery. Run `npm run verify`, native tests, supported-volume tests and secret-output assertions. Document live checks separately.
